# Phase 2 Implementation Plan — Fraud Extraction, gRPC, and Containerization

**Status:** Planned (Phase 2 start)
**Predecessor:** Phase 1 (done — Spring Boot monolith, PostgreSQL, unit tests)
**Successor:** Phase 3 (Kafka, Redis locks/idempotency, Testcontainers everywhere)

This plan operationalizes the PRD Phase 2 scope: *extract the Fraud Detection Service, containerize both services with Docker, and replace in-process calls with gRPC.*

---

## 1. Target Architecture after Phase 2

```
                          ┌────────────────────────────┐
  REST /api/v1/transfers  │  Wallet Service (monolith) │
 ─────────────────────────►  - domain + application     │
                          │  - PostgreSQL (ACID)       │
                          │  - FraudEvaluationPort ────┼─── gRPC ───┐
                          └────────────────────────────┘            │
                                                                    ▼
                                              ┌──────────────────────────────┐
                                              │  Fraud Detection Service     │
                                              │  - rules engine (sync, <50ms)│
                                              │  - MongoDB (audit log)       │
                                              └──────────────────────────────┘
```

Two Spring Boot services, one Git repository (multi-module Maven), gRPC as the only
inter-service contract, MongoDB as Fraud's write-optimized store.

## 2. Repository Restructure (Multi-Module Maven)

Convert the single-module build into:

```
pom.xml                     (parent: BOM, java 21, plugin management)
grpc-contracts/             (proto files + generated stubs, published to reactor)
wallet-service/             (current src/ moved here, gains gRPC client)
fraud-service/              (new Spring Boot service, gRPC server)
docker-compose.yml          (updated: postgres + mongo + both apps)
Dockerfile.wallet-service
Dockerfile.fraud-service
```

**Why one repo, multi-module (not separate repos):** the PRD treats this as a
portfolio showcase; a single repo keeps the review simple and lets
`grpc-contracts` be a plain reactor module instead of a published artifact.
Phase 4 CI can still build/test each service independently.

**Steps:**
1. Create parent `pom.xml` with `dependencyManagement` (Spring Boot BOM import).
2. Move current code to `wallet-service/`; verify `mvnw verify` still passes.
3. Create empty `fraud-service/` module (Spring Boot, no web server initially —
   it exposes gRPC and optionally actuator only).
4. Create `grpc-contracts/` module with `protobuf-maven-plugin` + `os-maven-plugin`
   (protobuf 3.25.x, grpc-java 1.6x).

## 3. gRPC Contract (`fraud/v1/fraud.proto`)

```protobuf
syntax = "proto3";
package fraud.v1;

service FraudEvaluationService {
  // Synchronous, latency-sensitive. Must respond within the caller's deadline.
  rpc EvaluateTransaction(EvaluateTransactionRequest) returns (EvaluateTransactionResponse);
}

message EvaluateTransactionRequest {
  string transfer_id = 1;          // generated by wallet service (UUID)
  string source_wallet_id = 2;
  string destination_wallet_id = 3;
  string amount_minor = 4;         // integer cents, avoid float rounding
  string currency_code = 5;        // ISO-4217
  google.protobuf.Timestamp requested_at = 6;
}

message EvaluateTransactionResponse {
  Decision decision = 1;           // APPROVE | REJECT | REVIEW
  string rule_id = 2;              // which rule fired ("" if none)
  string reason = 3;
}

enum Decision { DECISION_UNSPECIFIED = 0; APPROVE = 1; REJECT = 2; REVIEW = 3; }
```

**Contract rules:**
- Versioned package `fraud.v1` — additive evolution only (never reuse field numbers).
- Money as **minor units string** (integer cents) to dodge float artifacts.
- `REVIEW` is accepted by the contract now but Phase 2 wallet behavior treats it
  as APPROVE (manual-review workflow is out of scope); documented in ADR-005.

## 4. Wallet Service Changes (Client Side)

1. **Application layer:** new driven port `FraudEvaluationPort` with method
   `evaluate(FraudEvaluation) -> Decision`. `TransferApplicationService.transfer()`
   calls it **before any lock or debit** — reject early, pay no lock costs on
   fraud rejections.
2. **Infrastructure adapter:** `GrpcFraudClient` implementing the port
   (`grpc-stub` + managed channel). Deadline: **300ms** per call.
3. **Resilience (Resilience4j):** TimeLimit 300ms → Retry (2 attempts, only on
   UNAVAILABLE, no retry on REJECT) → CircuitBreaker (50% failure rate, half-open
   after 10s). Configured via `application.yml`.
4. **Failure semantics: fail-closed** — if fraud is unreachable after retries and
   the breaker is open, the transfer is refused with `503 Service Unavailable`.
   For a payments core, never moving money without a risk opinion is the
   defensible default. Recorded in **ADR-005**.
5. Startup must not require Fraud to be up (lazy channel); health endpoint gains a
   fraud-connectivity indicator only in logs/metrics, not a hard dependency.

## 5. Fraud Detection Service (Server Side)

1. **gRPC server** exposing `FraudEvaluationService` (plain grpc-java via the
   Spring context; port 9090). No REST surface.
2. **Rules engine** (strategy pattern, ordered pipeline, all synchronous):
   - `R1-amount-ceiling`: single transfer above configurable limit → REJECT.
   - `R2-velocity-source`: N debits from same wallet within window (rolling 60s,
     configurable) → REJECT. Counters in memory (Caffeine) in Phase 2 — the
     cross-instance Redis version arrives with Phase 3.
   - `R3-self-transfer`: redundant defense (wallet also enforces) → REJECT.
3. **Audit persistence:** every evaluation (request, decision, rule, latency)
   written to MongoDB (`fraud_evaluations` collection, TTL index optional) via
   async writer (bounded queue) so the gRPC response path never blocks on I/O.
4. **Observability:** Actuator + Micrometer metrics: evaluations total by decision,
   rule latency histogram, breaker-aware error ratio.
5. Testing: unit tests per rule; a gRPC integration test with a real server on an
   ephemeral port.

## 6. Dockerfiles (Multi-Stage)

Per service (`Dockerfile.wallet-service`, `Dockerfile.fraud-service`):

```dockerfile
# ---- build ----
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /workspace
COPY . .
RUN --mount=type=cache,target=/root/.m2 mvn -pl wallet-service -am -DskipTests package

# ---- runtime ----
FROM eclipse-temurin:21-jre-alpine
RUN addgroup -S app && adduser -S app -G app
USER app
COPY --from=build /workspace/wallet-service/target/*.jar /app/app.jar
ENTRYPOINT ["java","-jar","/app/app.jar"]
```

- Layer-cached Maven repo (`--mount=type=cache`).
- Non-root user, JRE-only runtime (Alpine now; distroless swap is a one-line change).
- Healthcheck in compose via actuator (`wget -qO- localhost:8080/actuator/health`).
- `.dockerignore`: `target/`, `.git`, `.idea`, `docs/`.

## 10. Explicit Non-Goals (deferred)

- Kafka events, Redis locks/idempotency keys (Phase 3).
- Distributed tracing (Phase 4 — local actuator metrics only).
- Manual-review workflow for `REVIEW` decisions.
- Cross-instance velocity counters (in-memory until Redis, Phase 3).

## 11. Open Decisions (recommendations, can be overridden)

| Decision | Recommendation | Alternative |
|---|---|---|
| Fraud failure semantics | **Fail-closed (503)** | Fail-open (approve w/o risk opinion) — not recommended for payments |
| Velocity counters store | In-memory Caffeine (Phase 2) | Redis immediately — pulls Phase 3 work forward |
| MongoDB | Real MongoDB 7 container | Skip audit persistence in Phase 2 — weakens the showcase |
| REVIEW decision | Treated as APPROVE in Phase 2 | Reject REVIEW — more conservative, same effort |
